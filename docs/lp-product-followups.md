## 壁打ちで合意したこと

- 人からAIへ任せるだけでなく、AIが依頼主になって人へ仕事を頼めることをGuilduoの中心に置く。
- Agentはユーザーが普段使う外部AI。登録・接続・タスク操作をつなぎ、固定の公式人格を前提にしない。
- Guilduoは依頼・進捗・FBをテキストで共有する。成果物の閲覧・実行・編集は外部の作業環境で行う。
- AIが人に頼むにはSkillsや運用ルールが必要。MCP接続や担当割り当てだけでAIが自動起動・自動判断する仕組みにはしない。
- 利用例はVibeコーディングのタスク・実機FB、OpenClawの更新や確認。LP制作後に本体とSkillsを改善する。
- 公式コピー・色・アイコンを継承する。楽しさは仕事の受け渡しや自分のFBへの反応から生む。

## 着手時の土台と不足（aa884c1時点）

| 観点 | 現行ソースで確認できること | 後続で補うこと |
| --- | --- | --- |
| 担当・関連 | `assignee`、`parentQuestId`、`dependencyIds`が存在する | 依頼主の記録、AI起点のHuman確認依頼との関係 |
| Handoff | Agent担当Questの`review_required → accepted / working`と理由付き修正依頼がある | 独立したHuman確認Quest、保留・再開・再確認をつなぐ導線 |
| 完了 | Handoff遷移はQuest完了と別。子完了で親を自動完了しない | 本体UIの承認後の見せ方もこの区別へ揃える |
| 成果物 | `artifactUrl`とテキストのnoteを保持できる | 内部Evidenceプレビューを前提とする判断ゲートを外部確認の手順へ合わせる |
| 受信 | Attentionの介入モデルとAlerts件数がある | Human宛て依頼の新着・未対応・保留の受信体験は実動作の確認と実装が必要 |
| Skills | 一般的なQuest作成・Handoff・人の承認が記載済み | AIが人を頼る判断基準、依頼テンプレート、回答待ち・再開・重複防止 |
| Agent接続 | Registry・OAuth接続・Agentリンクと実効権限の取得ができる | 現在のAgentと読取/更新可否を初回利用者が把握する導線 |
