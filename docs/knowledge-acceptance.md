# Relay Memory: implementation and acceptance

The production code deploys with both feature flags disabled. Paid services, human-confirmed gold data and real ChatGPT Web / Claude Code / Codex acceptance are pending. Additional authorized spending is **¥0**. No actual Quest or Agent is bound to this coding session.

## What the candidate implements

- Migration `0019_shared_knowledge.sql` adds independent D1 items, sources, revision history, native projects and Quest associations, sharing settings, content-free idempotency receipts/tombstones, conflicts and indexing outbox. Existing Private Notes and Appwrite Quest state are untouched.
- MCP `get_work_context`, `capture_knowledge`, `search_knowledge`; equivalent REST domain functions. Knowledge-read/write scopes require explicit OAuth and Agent policy grants plus the owner's approval of a specific connection and Agent. A change in connection membership invalidates that approval. OAuth with omitted scopes and new Agents' defaults exclude knowledge; existing records are never expanded. Human-only origin-protected management handles sharing, project identities, history, undo, conflict resolution, deletion and exports.
- Literal D1 search covers Japanese short strings and API/error identifiers. This owner-scoped scan is an initial baseline, not a claimed large-scale FTS benchmark. Context is capped by count and bytes with explicit continuation. Project scope is applicability, not per-project access control.
- Vectorize candidates are checked against current owner/revision/status in D1. Content-free Queue hints always resolve the current outbox generation; duplicate/out-of-order hints cannot change knowledge. Failed dispatch/processing leaves the outbox retryable. Old vector IDs remain in a content-free reconciliation inventory. A provider's accepted asynchronous deletion is not proof of immediate physical erasure; D1 excludes deleted content immediately. Index cleanup can remain pending while external operations are disabled.
- Index generation freezes the configured model and dimensions. No server generative LLM. Working Agents submit the small extracted facts, source metadata and epistemic kind. Agent claims of verified access are downgraded; `system_verified` cannot be self-attested. Knowledge does not change formal Human responses, Handoff acceptance, completion, XP or rewards.
- Web Settings: permission selection, listing/search, editing applicability and reasons, conflicts, history/undo, deletion and JSON export. Quest details load related knowledge and can associate a native project after settings are loaded. Existing controls/tokens are reused; no new dependencies.
- Canonical Skill/references and local lifecycle guidance describe automatic start retrieval and meaningful-boundary capture within explicit sharing authority. Hooks still do no network I/O, credential/transcript reading or direct MCP calls. Their exact session/Quest/Agent binding and recursion/trust rules remain. Public packages remain hookless; prompts cannot guarantee ChatGPT invocation or suppress host confirmation dialogs.

Final success: all critical demo UI/API requirements; ≥11/12 continuation successes; zero tested unauthorized access, deleted-content returns, invented formal approvals, duplicate mutations, lost updates or serious applicability errors. Record repeated explanations, rework and resume time. A local fixture pass covers the isolated Worker and browser. Host acceptance needs its own captured evidence.

`tools/evaluate-knowledge.mts` only scores supplied observed records; it performs no provider calls. Inputs are the confirmed case file and `{frozenModel?,runs:[{model,results:[...]}]}`. Each result needs `caseId`, retrieved expected keys, `latencyMs`, `captureCorrect`, `continued`, `criticalRequirementsMet`, `humanReviewed`, `repeatedExplanations`, `reworkCount`, `resumeMs` and `violations`. Missing cases cannot pass. Use model labels `baseline`, `lexical`, `bge-m3`, `plamo-embedding-1b`. Final scoring requires one complete run whose model matches `frozenModel`. Record a serious violation even when the rest of that case succeeded.

## Staged rollout and rollback

1. Apply additive D1 migrations through 0020 before deploying Worker and then Web. On production, deploy with the flags disabled. Before enabling, use a named owner-only verification environment and complete the applicable owner gates. Do not migrate Quest state or replace private productivity storage. The owner-only acceptance run requires explicit sharing and connection grants in the verification environment.
2. Lexical-only testing requires `KNOWLEDGE_ENABLED=true`, the existing `QUESTFORGE_DB` and the selected owner's `KNOWLEDGE_OWNER_UID`. Release config refuses an enabled beta without this owner. Other users are denied, and Queue dispatch/processing is limited to that owner. Owner manages sharing through Web; OAuth/Agent scopes stay opt-in. Deploying itself uses account quotas, so it is not performed by the local implementation check.
3. After monetary approval and model selection, configure `KNOWLEDGE_EXTERNAL_APPROVED=true`, `KNOWLEDGE_AI`, `KNOWLEDGE_VECTOR`, `KNOWLEDGE_QUEUE`, model/dimensions, a fixed `KNOWLEDGE_BUDGET_ID` and positive `KNOWLEDGE_MAX_EMBEDDING_REQUESTS`. The DB reserves every AI attempt **before** calling out, including timeouts/failures; no auto-refund or automatic new budget ID. This request cap bounds AI attempts, not total Cloudflare cost. The approved monetary cap must include other services and account-level spend controls. Never enable these settings under the current ¥0 authorization.
4. Release config generation accepts optional binding names `KNOWLEDGE_VECTOR_INDEX` and `KNOWLEDGE_QUEUE_NAME` only for the approved external campaign. Create resources/index dimensions deliberately; no deploy/create command is part of the default build or tests. Cron retries the durable outbox; Queue delivery is at least once. If indexing fails, show lexical fallback rather than discarding saved facts.
5. Monitor queue/job count, attempts, latency, failed dispatch/processing count and budget usage without content. For bounded local inspection, query `knowledge_index_jobs` and `knowledge_embedding_budget`; do not log request bodies or provider exceptions. No knowledge TTL deletion is scheduled.
6. Disable `KNOWLEDGE_EXTERNAL_APPROVED` to stop new external work and keep lexical access. Disable `KNOWLEDGE_ENABLED` to return to the old product behavior; keep the additive data/migration for recovery. Do not drop tables as rollback. Pending deletions still need provider cleanup after an approved environment is restored.
7. Same-model rebuild: in the approved test database, requeue current item revisions into `knowledge_index_jobs` (active→upsert; deleted/superseded→delete), preserving existing entries/tombstones and budget accounting; verify retrieval/readback afterward. A model/dimensions change needs a new index and an explicit migration of the frozen config, never an environment-variable-only switch. There is no automatic paid rebuild.
8. Only after real owner acceptance, record the actual three-host workflow for LP material. No mocked recording, autonomous launching, full-chat storage, 3D graph or Party/cross-user sharing is included.
